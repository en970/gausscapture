Audit defects D01, D02, D05, D08, D10, D18, D19, D21, D24, D28, D29 and the storage half of D14 are **already fixed**. Live capture guidance\n\nFive layers, ordered by how little attention each demands.\n\n### L0 · Haptics (zero visual attention)\n\n- 30 ms on start, 20 ms ×2 on stop — already present.\n- **One** 40 ms buzz on *entering* a warn state. Silence on clearing. Never repeat while warned; repetition trains the operator to ignore it.\n- Pacing ticks at 25 / 50 / 75 % of `targetSeconds`, distinct double-tick at 100 %. This answers \"am I done yet\" with no glance at all.\n\n### L1 · Perimeter state border (peripheral vision — highest value, does not exist today)\n\n8 dp border inset around the preview. Idle: none. Recording + good: `#2EFFFFFF`, static. Recording + warn: `#FFB020` at 100 %, pulsing 1.2 s.\n\nAt 550 mm with gaze on the subject, the screen is in the peripheral field, which is motion- and luminance-sensitive but detail- and colour-poor. A pulsing high-luminance perimeter is detectable *without foveating*; a centred word is not.\n\n### L2 · The one word (foveal, once the perimeter has earned the glance)\n\n44sp/800, `#0B0F14` on an opaque `#FFB020` pill, 20 dp radius, 24 dp horizontal / 16 dp vertical padding, centred at ~40 % screen height. Glyph to the left of the word — never colour alone.\n\n**Strict single-slot priority queue**, one message ever:\n\n| Priority | State | Word | Condition |\n|---|---|---|---|\n| 1 | write/storage failure | `Writing failed` / `Card is full` | `JsonlWriter.failure() != null`, or `Storage.freeBytes() < 2 GB` |\n| 2 | too fast | `Slow down` | `blur_px > 2.0`, clears below 1.4 |\n| 3 | too dark | `Too dark` | `stops_short > 0.5`, clears below 0.2 |\n| 4 | no parallax | `Walk around it` | pure-pan sustained > 2 s |\n| 5 | — | *(silence)* | success is silent |\n\nSignals 5+ from `RESEARCH.md` §S6 join this list only once validated. **Silence is the success state.** There is no \"good\" message, no persistent quality meter, and no composed 0–100 score — `RESEARCH.md` states the composed score is unvalidated and that validating it *is* the paper (S7), so putting it on the viewfinder would both mislead the operator and contaminate the correlation study.\n\n### L3 · Time-to-target (deliberate glance)\n\n6 dp ring around the record button, `#33FFFFFF` track / `#E6FFFFFF` fill, clockwise 0 → target, staying neutral at 100 % (the haptic double-tick carries completion). `0:42` in 32sp tabular mono above; nothing here is fitted.\n\n**Blur — pan/roll decomposition.** The current `SensorLogger.blurPixels(|ω|, t, f)` uses the full gyro magnitude, which over-counts roll: rotation about the optical axis produces zero blur at the image centre and radially increasing blur outward.\n\nA useful simplification: the sensor→camera map is `diag(1,−1,−1)`, so component *magnitudes* are unchanged, and both `sqrt(ωx²+ωy²)` and `|ωz|` are invariant under rotation about z. **The image roll never enters the formula**, so raw device-frame gyro components can be used directly.\n\n```\nblur_pan  = t_exp · f_px · sqrt(ωx² + ωy²)              // uniform image translation\nblur_roll = t_exp · |ωz| · r_max ,  r_max = 0.5·sqrt(W² + H²)   // worst case, at the corner\nblur_px   = sqrt(blur_pan² + blur_roll²)\n```\n\nAt 1080p, `r_max = 1101 px` against `f_px ≈ 1300–1400`, so this slightly *reduces* the roll term and correctly labels it a corner worst case. Warn at 2.0 px, clear at 1.4 px, 900 ms minimum dwell. `f_px` is `fx_o` from §3.2 of the intrinsics chain, **not** raw `LENS_INTRINSIC_CALIBRATION[0]`.\n\nBudget table (1080p, `f_px ≈ 1300`, pure pan) — this is why decision #6 matters:\n\n| `t_exp` | ω for 1 px | ω for 2 px |\n|---|---|---|\n| 1/30 s | 0.023 rad/s = 1.3 °/s | 2.6 °/s |\n| 1/60 s | 0.046 = 2.6 °/s | 5.3 °/s |\n| 1/125 s | 0.092 = 5.3 °/s | 10.6 °/s |\n| 1/250 s | 0.192 = 11 °/s | 22 °/s |\n| 1/500 s | 0.385 = 22 °/s | 44 °/s |\n\nA comfortable handheld orbit is 20–30 °/s. At AE's typical indoor 1/30 s that is **22 px of smear**.\n\n**Exposure health, in stops:**\n\n```\nstops_short = log2( (t_ae · iso_ae) / (t_cap · iso_max) )\n```\n\n`> 0` means it is physically impossible to hit the blur target at this light level. Warn at `> 0.5`, clear at `< 0.2`. Computable from `CaptureResult` alone, no pixels.\n\n**Pure-pan detector** (rotation without translation ⇒ zero parallax ⇒ 3DGS fails):\n\n```\na_lin = | a_measured − R_world_from_device^T · g |     // gravity removed via TYPE_ROTATION_VECTOR\nif RMS(a_lin) < 0.15 m/s²  AND  |ω| > 0.3 rad/s  sustained > 2 s  →  \"Walk around it\"\n```\n\n**Suppress this warning entirely when `preset.expectedToFail` is true** — D_rotation is *supposed* to be rotation-only, and warning there would contradict the protocol.\n\n### 3.2 Exposure policy (decision #6)\n\nReplace `CONTROL_AE_LOCK` as the exposure policy. Gate on `MANUAL_SENSOR` in `REQUEST_AVAILABLE_CAPABILITIES`; wait for `CONTROL_AE_STATE == CONVERGED` in the *preview* session before reading, which also fixes audit D22 (locking in the same request that starts recording can freeze a not-yet-converged exposure):\n\n```java\nlong tCap = 4_000_000L;                       // 1/250 s\nlong tNew = Math.min(tAe, tCap);\nint isoNew = (int) Math.round(isoAe * (double) tAe / tNew);\nRange<Integer> isoR = ch.get(CameraCharacteristics.SENSOR_INFO_SENSITIVITY_RANGE);\nisoNew = Math.max(isoR.getLower(), Math.min(isoR.getUpper(), isoNew));\nb.set(CaptureRequest.CONTROL_AE_MODE, CameraMetadata.CONTROL_AE_MODE_OFF);\nb.set(CaptureRequest.SENSOR_EXPOSURE_TIME, tNew);\nb.set(CaptureRequest.SENSOR_SENSITIVITY, isoNew);\nb.set(CaptureRequest.SENSOR_FRAME_DURATION, 33_333_333L);\n```\n\nWithout `MANUAL_SENSOR`, fall back to today's `AE_LOCK` and additionally set `CONTROL_AE_ANTIBANDING_MODE_OFF` (50 Hz antibanding quantises `t_exp` to multiples of 10 ms and defeats any short-exposure policy). Record which path was taken in the manifest.\n\n---\n\n## 4. The recorded data contract\n\nEverything the app writes, and why the pipeline needs it.\n\n### 4.1 Clock alignment — the reason this app is native\n\nThis is the project's most valuable output and the constraint every other decision bends around.\n\n**What is guaranteed.** `SENSOR_INFO_TIMESTAMP_SOURCE == REALTIME` ⇒ `CaptureResult.SENSOR_TIMESTAMP` is on `CLOCK_BOOTTIME`, the same base as `SystemClock.elapsedRealtimeNanos()`, and comparable to other subsystems on that base. `SENSOR_TIMESTAMP` is specifically *start of exposure of the first row*. `SensorEvent.timestamp` is documented on the same base. REALTIME is **not** implied by any hardware level or capability and must be queried.\n\n**What is not guaranteed, and is already handled.** Several OEM builds ship sensors on `CLOCK_MONOTONIC` instead. `Clocks.observeSensorEvent()` measures this from the first event of each capture by comparing against both `elapsedRealtimeNanos()` and `nanoTime()` and taking the nearer. Keep this verbatim — it is correct and it is what audit D12 asked for.\n\n**The trap that is still live.** `OutputConfiguration.TIMESTAMP_BASE_DEFAULT` means that for a `MediaRecorder` surface the timestamp base is `TIMESTAMP_BASE_MONOTONIC` (uptime), *not* the sensor base. So **the PTS inside `video.mp4` and the `t_ns` in `frames.jsonl`/`imu.jsonl` differ by total suspend time since boot** — seconds to hours. Alignment survives today only because `gravity.py` pairs by row index, never by timestamp. Fix, verified present in `android-33/android.jar`:\n\n```java\nif (Build.VERSION.SDK_INT >= 33) {\n    OutputConfiguration oc = new OutputConfiguration(recorderSurface);\n    oc.setTimestampBase(OutputConfiguration.TIMESTAMP_BASE_SENSOR);\n}\n```\n\n`MPEG4Writer` still rebases the first sample to 0, so the *offset* is lost but the *deltas* become exactly comparable — which is what turns index alignment from an assumption into a checkable invariant.\n\n**Do not use `SystemClock.uptimeNanos()`** — verified absent from `android-33` and `android-34`, present only in `android-36`, i.e. API 35+. It compiles cleanly against the newest platform and throws `NoSuchMethodError` on an S22 running Android 13/14. `System.nanoTime()` is already used and is correct.\n\n**Empirical bracket, cheap and worth adding** in `onCaptureStarted`:\n\n```java\nlong dRealtime = SystemClock.elapsedRealtimeNanos() - tsNs;   // expect 0 .. 200 ms\nlong dUptime   = SystemClock.uptimeMillis()*1_000_000L - tsNs;\n```\n\nAccept the capture only if `0 ≤ dRealtime < 200 ms` for > 99 % of frames. A device that claims REALTIME but emits monotonic shows `dRealtime` equal to accumulated deep-sleep time, which is trivially separable. Record p50/p99 in the manifest.\n\n### 4.2 `frames.jsonl` — one row per frame, keyed on `frameNumber`\n\n**The problem.** Today `\"frame\"` is a self-incremented counter over `onCaptureCompleted` calls while `recording == true`, and `gravity.py:295` maps video frame → row via `by_frame[int(round(seconds * fps))]`. Nothing enforces that these are the same index. `onCaptureCompleted` is not delivered for failed captures, and a completed result does not imply a buffer reached the encoder. The offset is silent, unbounded, and undetectable after the fact. Gravity survives at 0.998 only because the accelerometer is slow-varying and averaged over the whole capture — the module's own docstring says a ±4-frame sweep moves the result by at most 1.58°. Pose seeding (ROADMAP S4) will not survive it.\n\n**The fix.** Keep a small `LongSparseArray<Long>` from `frameNumber → t_ns` filled in `onCaptureStarted`, and emit exactly **one** row per frame at whichever terminal callback fires:\n\n- `onCaptureCompleted` → full row\n- `onCaptureFailed` → `{\"frame_number\":n,\"t_ns\":…,\"dropped\":\"failed\"}`\n- `onCaptureBufferLost` (match `surface == recorderSurface`) → `…\"dropped\":\"buffer_lost\"`\n\n```json\n{\"frame_number\":1234,\"t_ns\":885123456789,\"readout_t_ns\":885123479000,\n \"exposure_ns\":4000000,\"iso\":320,\"focal_length_mm\":5.4,\"focus_distance\":0.0,\"aperture\":1.8,\n \"crop\":[0,0,4032,3024],\"zoom_ratio\":1.0,\"physical_id\":\"2\",\"lens_state\":0,\n \"ae_state\":3,\"awb_state\":3,\"af_state\":0,\"vstab\":0,\"ois_mode\":0,\"distortion_mode\":0,\n \"rolling_shutter_skew_ns\":25000000,\n \"ois\":[[885123456789,0.4,-0.2]]}\n```\n\n**Reader contract, to be stated in `CAPTUREPACK_SPEC.md`:** video sample *i* corresponds to the *i*-th row, ordered by `frame_number`, among rows with no `dropped` key. No `seq` field is written on device — it is derived, so it cannot go stale.\n\nField notes: `frame_number` is `CaptureResult.getFrameNumber()`, authoritative and monotonic, and gaps mean dropped requests. `readout_t_ns` requires API 34 (`SENSOR_READOUT_TIMESTAMP == HARDWARE` + `onReadoutStarted`) — verified absent in `android-33`, present in `android-34`; it gives a free per-frame check on `SENSOR_EXPOSURE_TIME`. `physical_id` is `LOGICAL_MULTI_CAMERA_ACTIVE_PHYSICAL_ID` (API 29), the lens-switch detector, already logged. `ois` is present only when `STATISTICS_OIS_DATA_MODE_ON` was accepted; each entry is `[t_ns, xshift_px, yshift_px]` in pre-correction active-array pixels, on the same timebase as `SENSOR_TIMESTAMP`, and the true per-frame principal point is `(cx + xshift, cy + yshift)`. **If the Samsung HAL ignores `LENS_OPTICAL_STABILIZATION_MODE_OFF` — common — this is the only way to recover a valid intrinsic model**, because otherwise every frame has a different unknown principal point. The per-frame `ois_mode` readback tells you whether you need it.\n\n### 4.3 `imu.jsonl` — unchanged, deliberately\n\n```json\n{\"type\":\"android.sensor.accelerometer\",\"t_ns\":885123456789,\"t_rel_ns\":1234567,\"v\":[0.12,-9.78,0.33],\"accuracy\":3}\n```\n\n`type` via `Sensor.getStringType()` is the exact literal `gravity.py:38` matches on. Absolute `t_ns` is the primary key — it is what lets a frame find its sample and what makes the 0.998 alignment possible; `t_rel_ns` is alongside only because it is readable. Uncalibrated variants carry 6 values and their distinct type string keeps them from contaminating the 3-axis reader. Five sensors stay registered. **Do not change this schema** — it is the one thing measured to work.\n\nTwo refinements that do not touch the schema: register with an explicit period and `maxReportLatencyUs = 0` rather than `SENSOR_DELAY_FASTEST` (`registerListener(l, s, 2500, 0, handler)` = 400 Hz; batching would keep events in the hardware FIFO and deliver them late, which ruins live guidance), and consider adding `TYPE_GAME_ROTATION_VECTOR` (no magnetometer, so no indoor magnetic disturbance). `HIGH_SAMPLING_RATE_SENSORS` is already declared and is required above 200 Hz from API 31.\n\n### 4.4 `intrinsics.json` — the crop/scale/rotate chain, made auditable\n\nPreconditions that make the chain exact, all already set or settable: `DISTORTION_CORRECTION_MODE = OFF` (so the crop region shares the pre-correction coordinate system with the intrinsics), `CONTROL_ZOOM_RATIO = 1.0f`, and `SCALER_CROP_REGION` never set in the request.\n\nWith `A` = `SENSOR_INFO_PRE_CORRECTION_ACTIVE_ARRAY_SIZE`, `C` = per-frame `SCALER_CROP_REGION` **from the result** (the HAL adjusts it, and video stabilisation modifies it), output `(W_o, H_o)`:\n\n```\nar_o = W_o/H_o ;  ar_c = C.w/C.h\nif ar_o >= ar_c:  used_w = C.w ;          used_h = C.w/ar_o\nelse:             used_h = C.h ;          used_w = C.h*ar_o\nused_left = C.left + (C.w - used_w)/2\nused_top  = C.top  + (C.h - used_h)/2\ns = W_o / used_w\nfx_o = fx*s ;  fy_o = fy*s\ncx_o = (cx - used_left)*s ;  cy_o = (cy - used_top)*s ;  skew_o = skew*s\n```\n\nThe current `focalPixels()` (`calibration[0] * videoWidth / active.width()`) happens to be **correct for `fx` in the default case** (`C == A`, 4:3 array, 16:9 output), which is why it has not caused visible trouble. The live bug is the principal point: `intrinsics()` publishes raw `cx, cy` with a note to \"rescale\", but for a 16:9 stream out of a 4:3 array `cy` needs `used_top = 0.125·A.height` subtracted *before* scaling. Scaling alone puts it ≈ 135 px off vertically at 1080p.\n\n**Pixel-centre convention:** Android places the centre of pixel *(x,y)* at *(x+0.5, y+0.5)*, so a perfect optical centre on a 10×10 array is at *(5.0, 5.0)*. This is **0.5 px offset from the OpenCV convention** where the ideal centre of a W-wide image is *(W−1)/2*. State the convention in the file.\n\n**Orientation (decision #5).** `setOrientationHint` writes a display matrix that `ffmpeg` applies by default, so extracted frames are display-upright while the intrinsics are in the sensor frame. The measured `diag(1,−1,−1)` with *no roll term*, on a device whose `SENSOR_ORIENTATION` is 90, is positive evidence the frames reaching SfM are already upright — so the hint stays and the intrinsics are rotated to match.
